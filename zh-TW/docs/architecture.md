# 這個倉庫為什麼要拆成這幾層

一開始把所有規則寫進同一份 Prompt 很方便，但規模一大就會遇到兩個問題：同一件事在不同段落被寫了兩次，以及後來根本不知道哪一份才算準。這個倉庫的結構主要就是為了解決這兩件事。

`rules/` 放真正需要遵循的規則，也是唯一應該修改規則語意的地方。像「什麼時候必須詢問」、「怎樣才算真的測試過」都屬於這裡。

`workflows/` 比較像路線圖。它把既有規則排成實際工作順序，例如 Bug 修復會先重現、追資料流、驗證假設，再開始改。Workflow 本身不另外發明政策，這樣未來 Rule 改了，不必到三四份流程文件找相同句子。

`gates/` 是階段性的檢查點。它們很適合放在 Commit、Push、Release 前，因為這些時候需要的是一張短清單，而不是重新讀一整份工程手冊。每個 Gate 也標示了誰負責確認，以及應該留下哪些證據。

`templates/` 處理的是產物長相，例如 README、AGENTS、專案記憶與工作紀錄。Template 可以改排版，但不應偷偷改治理規則。

`docs/` 則完全站在人類讀者角度寫。這裡可以談背景、取捨、例子和不同工具怎麼接，但不會用另一套措辭重新定義 Rule。若 Docs 和 Rule 看起來有衝突，以 Rule 為準，然後修正文件。

`scripts/` 只自動化能客觀判定的事情。像 UTF-8、斷掉的相對連結、重複 Rule ID 或版本漂移，很適合交給 Validator；「某個架構是不是過度設計」則仍然需要工程判斷，不應假裝用腳本就能回答。

整體可以把它想成：Rule 決定原則，Workflow 告訴你怎麼走，Gate 確認現在能不能往下一步，Template 幫你產生一致的文件，而 Docs 負責讓這些東西容易理解。
