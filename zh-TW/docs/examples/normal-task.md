# 範例：一般功能修改

假設需求是「讓設定檔支援新的 `timeout` 欄位」。這種工作不需要啟動完整 Release 流程，但也不該看到一個設定檔就直接加 key。

先看目前設定是在哪裡解析、預設值放哪裡、是否有 schema，以及設定物件最後被哪些模組使用。這一步通常已經能回答大部分問題，也符合 `CORE-001` 和 `DEC-001`：能從程式碼自己確認的事情，不需要再問使用者。

如果 `timeout` 只是既有設定系統裡新增一個普通欄位，可以沿用原本 pattern。若需求其實意味著要把整套 JSON 設定換成 YAML，這就不再是小改動，需要回到 Decision Policy 評估是不是另一個任務。

修改完成後先跑 parser / syntax check，再跑和設定載入直接相關的測試。若這個設定會影響服務啟動，也值得做一次 smoke test。最後看 diff，確認沒有因 formatter 把整份設定檔重新排序。

準備 Commit 時，Pre-commit Gate 應該能留下很簡單的證據：看過 `git status`、staged diff 是預期內容、相關測試真的跑過。這樣就夠，不需要為每個小改動寫一份冗長報告。
